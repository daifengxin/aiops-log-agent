# 「10 倍日志量扩容」架构演进方案

## 目标与约束

目标是在日志量提升 10 倍时保持异常检测延迟、诊断准确性和告警可读性，不把每条日志或每个异常窗口都交给 Gemini。当前原型是单机 Python 流程，扩容后应把“日志接入、窗口聚合、检测、RAG、LLM 诊断、告警抑制”拆成可独立扩展的链路。

## 演进架构

日志先进入 Kafka，按 `service + time_bucket` 分区，Flink 或 Kafka Streams 做 1s/10s/60s 滑动窗口聚合，只把窗口指标和少量样本日志写入检测服务。检测服务保持无状态横向扩展，输出异常事件到 `anomaly-events` topic。RAG 从本地词法检索演进为独立向量检索服务，索引 Kubernetes 文档、Runbook 和历史故障复盘，诊断服务按异常事件拉取 Top-K 上下文后调用 Gemini。

## 关键策略

- 接入层：Kafka topic 按服务和租户拆分，保留原始日志短周期热存，长期归档到对象存储。
- 窗口层：Flink 维护 EWMA/Z-Score 所需状态，状态后端使用 RocksDB，checkpoint 到对象存储。
- 检测层：只消费聚合指标，输出结构化异常事件，避免 Python 进程持有全量日志。
- RAG 层：向量库服务化，索引预构建；诊断时只传 Top-K 片段和异常摘要。
- Gemini 层：只对告警抑制后的代表异常调用；同一 `service + anomaly_type + root_cause` 在抑制窗口内复用诊断。
- 告警层：先合并重复窗口，再按根因、影响服务和置信度生成一条可执行告警。

## 落地顺序

第一阶段保留现有检测算法，先把日志读取改成流式聚合输入；第二阶段引入 Kafka/Flink，拆出异常事件 topic；第三阶段把 RAG 和 Gemini 诊断服务化，加缓存、限流和超时降级；第四阶段补齐监控面板和容量压测。

## 风险与观测

主要风险是窗口状态膨胀、异常事件风暴、向量检索延迟和 Gemini 配额耗尽。监控必须覆盖 Kafka lag、Flink checkpoint 时长、检测吞吐、异常事件 QPS、RAG P95、Gemini 调用量/失败率、告警抑制率、端到端诊断延迟和每千条日志成本。
